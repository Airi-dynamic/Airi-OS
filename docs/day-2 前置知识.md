# Airi 的少量笔记

> 由于在有 AI 的时代记笔记是非必要不值得做的事情，这里只有零散的记录，包含必须知道才能高效开发的东西。

问 AI，一般可以得到的答复是，现代计算机的启动流程是：
0. 计算机硬件启动
    - 电源管理电路本身通电后，做一些硬件层工作
    - 完成后 CPU 从“复位状态”释放，从复位向量执行第一条指令。
1. BIOS/UEFI “固件“运行
    - 它可以”初始化硬件“
    - 包括所谓的“内存、总线、外设（PCIe设备）”
2. BIOS/UEFI 加载引导程序（Bootloader）并运行
    - 从磁盘读取一个身份特殊的文件
    - 作为“UEFI 应用程序”运行
    - 可以”找到并加载操作系统内核“
3. 引导程序加载操作系统内核（Kernel）
    - 读取 ELF
    - “加载段，配置页表和内核栈”
    - 准备 Boot Information
4. 内核初始化
    - CPU 跳转到内核“入口点”并开始执行
    - 这里涉及到了 Airi-OS 的可见源代码
5. 内核启动完成，开始运行第一个用户态进程
    - 此时 Airi-OS 已经可以视为启动结束

## 世界观 1 ：最小计算设备

在一个架空的技术世界里开始。

这个世界已经拥有成熟的电学、半导体制造工艺和数字逻辑设计能力。美国现在有一批高新技术企业能够制造标准化的硬件寄存器、存储单元、逻辑运算电路，有成熟的智能温控面包机之类的东西。它们都是简单状态机，其逻辑由金属物质结构存储，不可修改，没有人试图把它们抽象出来，因此世界上不存在软件。

为了制造通用计算机，这些企业认为需要抽象出一套基本运算，现代化的语言来讲就是指令集。这些公司里的电路理论（本科生 / 研究生 / 博士生）认为，计算机的指令集应该是一个有限状态机的集合，面包机和微波炉的状态机不应该由它们自己用电路做，这是重复劳动。

他们首先设计了一个指令集，称为 RV32I，这是图灵完备的，所以理论上讲任何需要都可以用实现了它的硬件来做。然后，它们设计了一个 CPU，称为 RV32I CPU。这个 CPU 是一个有限状态机，它的状态由寄存器和内存组成，它的输入是指令，它的输出是寄存器和内存的变化。具体设计结果就是你武计院本科数电用 Verilog 设计的那个。然后还接上了真正的内存，磁盘之类的东西。

在仿真和开发调试这个 CPU 的时候，我们的核心工作是解决流水线正确性之类的问题。但当我们想要交付结果时，有一些开发环境会迫使我们开始设计现代计算机的启动流程：
1. clk 从哪来？
    - 真实世界没有 verilog 仿真qick 的时钟信号，只有电源管理电路的电压。我们要抽象出离散的时钟信号，才能实现理论上依赖状态迁移的 CPU。
2. reset 从哪来？
    - 芯片刚获得供电时，各个内部电路不一定已经进入我们想要的状态。必须有办法让 CPU 从一个确定的起点开始工作。
3. 指令在哪？
    - CPU 能执行指令，但你设计的 CPU 本身未必保存了任何指令。
    - 它输出地址以后，必须有另一个实际存在的硬件，将对应的机器码返回给它。

这意味着：这个计算机首先缺少的不是强大的 CPU，而是能够让 CPU 正常工作的外部环境。
上面三个具体问题可以抽象为三个问题：

1. 状态机的运行时环境需要建立
2. 状态机的初始状态需要设置
3. CPU 作为一个状态机太过抽象
    - 需要将其限制为一个更小的状态机，才能让它（更容易被用户用来）完成具体的工作。
    - 这个更小的状态机最终是 OS，这里我们需要关注状态机怎么实现缩小

于是引入以下概念（这些概念全部是计算机体系结构设计实现的）：
- 复位状态 Reset
    - CPU 在这个状态下，被限定为一个初始状态，寄存器都不变
    - 只有外部电路（时钟等）好了以后，它才会允许状态改变
- ROM（只读存储器）
    - 复位结束后，CPU 要改变状态需要指令输入
    - 这里为了跑起来先引入了只读存储器来存一个死循环指令
    - 目前暂时理解为跑马灯程序吧，这也可以说是一个”实际业务程序“
    - 具体实现是多样的，可以是存储硬件，可以是电路连线，毕竟存储器本身也是简单状态机
- MMIO（内存映射 I/O）
    - 只读存储器怎么和 CPU 连起来？
    - 指令集 ISA 模型只有寄存器，地址空间等概念
    - 因此我们将某个特殊的地址（例如0xFFFFFFF0）对应到这个 ROM
    - 在反映体系结构设计的硬件连线层面，我们设计为访问这个地址意味着从这个连线收电信号

这个 ROM 我们叫做**固件**。
固件代码是在操作系统还不存在于运行环境中时，CPU 也必须能够访问并执行的一段预先存储的代码。

## 世界观 2 ：存储系统

现在有些更复杂的问题要处理。
ROM 本身没有体现出逻辑和数据的分离，数据被隐含在了逻辑中。
数据量不大的时候没关系，但是如果要存文件，统计数据就必须引入 RAM。
由于 RAM 不能持久存储，ROM 又不可随意写，引入了 Flash（闪存）
    - 这里注意闪存包含了用各种工艺实现的持久存储。
    - 这个名字的意思是一种存储技术的集合

到这里还没有完，一个存储芯片无论如何实现它都是外围设备，和 CPU 没有本质关联。但为了形成完整计算机系统，我们必须建立将其与 CPU 的指令访问相连。

现在考虑这个 Flash，这是我们的实习生刚刚造出来的，再考虑这个 RAM，它是我们从隔壁公司买过来的。我们计划通过 MMIO 来把它们和 CPU 相连。
但这个 Flash/RAM 与我们之前用寄存器甚至电路连线这样低级的手段实现的 ROM 是不一样的。为了做到大存储空间，查阅说明书和实习生工作报告后，我们发现这些硬件很复杂：
    - 买来的 RAM 里面主要用的是电容，以及高频对其进行数据刷新的逻辑电路
        - 我们用寄存器就可以做些简单的 RAM ，感觉还好
    - 这个实习生做的 Flash 其中则大量使用例如 MOSFET（浮栅型金氧半场效晶体管，我们在硬件茶谈的科普视频里看到的那种电子存储装置）
        - 我们不知道这个实习生是何方神圣
    - 这完全超出了我们的学习范围，我们就学过怎么连接电线和元件。之前我们自己拼的临时 RAM 有一组并行连线，可以供我们直接物理接入存储指令的实现，但现在没有了，我们要看说明书来想办法。

我们发现这些硬件都声称自己实现了一个逻辑电路计算器，也就是**（设备侧）控制器**，它们支持的协议（说明书上写的外部连线和通信方式）各自不一样，但大致都是：
    - 向外暴露几个可读或可写或兼而有之的寄存器
    - 有的还有一些可以向外连接的数据或信号线
我们通过这些东西可以操作这些设备的状态机，以操作其内部存储单元。

现在我们只需要实现一个自己的地址译码器（拦截特殊 MMIO 地址访问并路由到 CPU 侧的控制器）
以及一个 CPU 侧的控制器（把对应指令翻译成外部存储器的控制指令并与它们直接交互）

终于我们把 CPU 和存储设备连接起来了。下一步。

同时也需要注意，RAM 和 ROM 都是通过 MMIO 来和 CPU 连接的。
这就是**物理地址空间**的基本含义：一套给物理存储器和设备资源分配地址的规则。
一些受保留地址的访问行为对应了对于计算机设计者指定规范下，对应硬件的操作（例如某些外设的寄存器）



假设我们把一个**较大的**应用程序保存在 Flash 中。此时可以设计这样的启动顺序：
1. 通电后，CPU 从预定的复位入口取指，执行 ROM 中的少量启动代码。
2. 启动代码初始化 RAM 控制器（电路层行为，发挥想象力即可），使 RAM 进入可用状态。
3. 启动代码通过 Flash 控制器读取应用程序，将其复制到 RAM。
4. CPU 将 PC 改成 RAM 中的程序入口地址，开始执行刚刚加载的程序。

这很重要，因为我们这个操作是在执行“小程序加载大程序”的行为。用 ROM 存储 Airi-OS 这样超级大的程序是不现实的，但裸 CPU 又无法从磁盘启动程序（这很显然对吧，直接启动的后果你应该清楚，很慢）

一定要说的话，并不是所有程序都必须复制到 RAM 执行。对于现代通用操作系统，内核通常需要被加载到 RAM 中运行。

## 世界观 3 ：总线和设备控制器

现在我们的设备本身已经是一个非常强大的状态机，其状态空间足以解决任何图灵可计算函数，并且我们也能把希望它解决的问题装载进这个状态机。

现在新的问题是，为了卖出这个状态机，我们要接入一些和真实世界的其他业务有关的设备，例如温度传感器，打印机，灯泡。

首先解决一个小问题，我们现在在开发过程中遇到困难，我们发现没有足够好的手段将内部信息输出出来。
我们一开始只是用 MIMO 控制几个 LED 灯的亮灭来观察，这很符合直觉。

但是随着程序逻辑变得复杂，我们需要做持续输出的功能，这个功能的性能要求目前并不高，只是要输出一些文字，因此我们选择只用一根信号线，将要传输的数据作为单比特顺序数据流传输，通过设计专有硬件封装一些简单通信协议和输出寄存器等，来为内核提供输出到外部的能力。

因为它是逐个位串行传输的，所以叫串口。

输出不一定要用串口，直接用现代图形学的帧缓冲区绘制画面，或者用多根线路并行传输都可以，但串口由于非常简单，可以保证简单易使用，以至于在大部分内核功能都崩溃时，都可以通过简单的数个汇编指令成功输出，所以会存在。提供串口功能的硬件就是所谓的 UART（通用异步收发器），

不要细看以下表格浪费时间。

| 术语 | 含义 |
| --- | --- |
| Serial Communication（串行通信） | 一种按时间顺序逐比特传送数据的通信方式 |
| UART | 负责实现特定异步串行通信的硬件 |
| Serial Port（串口） | 对外提供串行通信能力的接口 |
| Serial Driver（串口驱动） | OS 中管理 UART 硬件的软件 |
| Serial Console（串口控制台） | 在串行通信通道上实现的文本输入输出界面 |
| -serial stdio | 将 QEMU 虚拟串口连接到宿主机的标准输入输出 |

好的回到正题，我们刚才要加硬件，加的外部硬件就是包括串口之类的非计算机设备。

显然我们要为这些设备提供一个抽象，让 CPU 不关心具体实现（也就是通信协议之类的）
这个通信系统抽象称为总线（Bus），举个例子，我们像上文那样会需要使用 `lw t1, 0(t0)` 之类的指令去访问 RAM，这个行为是需要电路实现的，如果没有 Bus，我们就需要在实现支持该指令集的那个 CPU 的时候直接在硬件层面规定这条指令的执行单元如何与 RAM 这个外部硬件交互，包括如何握手，如何传输，如何终止等。我们现在不希望为任何一个特定硬件做这种事。
我们只为 Bus 做这种事。Bus 是怎么样的取决于人的设计，这也是像数电实验课设计 CPU 时一样恶心的工作，这里我们就想象我们约定的硬件通信协议如下

```verilog
// CPU 发给互连的请求
output wire        mem_valid;
output wire        mem_write;
output wire [31:0] mem_addr;
output wire [31:0] mem_wdata;

// 互连返回给 CPU 的响应
input  wire        mem_ready;
input  wire [31:0] mem_rdata;
```

| 信号 | 含义 |
| --- | --- |
| mem_valid | CPU 当前发起了一次有效访存请求 |
| mem_write | 1 表示写，0 表示读 |
| mem_addr | 访问的地址 |
| mem_wdata | 写操作携带的数据 |
| mem_ready | 本次请求已经可以完成 |
| mem_rdata | 读操作返回的数据 |

不要细看这个表格，理解思想即可。我们要求 CPU 的硬件实现通过检查这些位的状态来实现相关外部数据传输指令。同时也要求外围设备自行实现兼容它。这会引入流水线设计上的变更（因为不同设备速度不一样，可能造成流水线等待），实际上会需要硬件层优化来掩盖延迟等。个人读者无力负担理解它们的成本，因此不要关心。

接下来我们还是无法完成外部设备接入。因为在我们开始想办法卖这个 CPU 之前，世界上已经有硬件间协作的需要，例如 I^2C 通信协议，这种协议是芯片间串行通信协议，和 Bus 类似，但它并不要求有 CPU 存在，也不和我们设计的协议一样。因此需要一个**设备控制器**来兼容。这里只需要知道有这个东西存在即可，不需要关心其实现，毕竟它功能很简单，你很容易发挥想象力。

现在我们的一段汇编指令可以对应设备操作了。

```asm
    lui  t0, 0x30000     # 控制器基地址
    addi t1, zero, 1

    sw   t1, 0(t0)       # CONTROL = 1，开始测量

poll:
    lw   t2, 4(t0)       # 读取 STATUS
    andi t2, t2, 1      # 检查完成位
    beq  t2, zero, poll # 未完成，继续查询

    lw   t3, 8(t0)       # 读取 DATA，得到温度
```

不要细看。总之，看起来很像是纯计算指令，但是由于我们上述引入的机制，它对应了一次温度计测量过程。
这段代码要完成其预期功能，作者必须知道这个设备的操作规则（也就是控制器的寄存器布局，不然作者不知道上文代码中的控制器基地址，不知道要检查完成位，不知道基地址偏移多少对应结果寄存器）。但是作者对上层封装的函数则是可以在不知道这些东西的情况下使用的。
这些代码现在是汇编，实际一般都用 C 编写。这也就是所谓的**驱动程序**。

## 世界观 4 ：中断，定时器和 DMA

上面的工作做完以后，我们的 CPU，现在应该叫做 **计算机** 更合适，因为非常通用***卖爆了***！我们在上海原来只住得起 31 平米的房子，现在搬进了 41 平米的小屋子。~~当然三代xx人和老干部虽然不会这些也一直都住的是 200 平米大豪斯~~
然而很快一方面我们遇到了性能问题。我们之前就提到外部设备速度可能很慢，但没有处理。
目前我们可以在死循环里一直轮询（Poll）等，但不能一直这样。

显然，我们引入了中断机制，CPU 硬件层面可以中断原本的指令流执行，保存状态，执行别的指令流，再返回，恢复状态，例如等到温度计有读数了再返回。
（这个和函数调用级别的跳转不一样，可以在无函数调用处发生，同时由硬件负责完全隐藏和封装）

多种设备的中断请求都体现为各自一根电线上的电信号，连接到一个硬件（中断控制器），管理优先级，是否接受响应等。为了实现这个机制，我们侵入式修改了 CPU 结构（加了中断处理指令，中断寄存器和连线等），写了中断控制器硬件，现在 CPU 可以挂起温度计去做计算了。

为了计时我们还专门写了计时器，它也接入终端控制器来为 CPU 提供符合物理的时间尺规。（CPU 自己的指令执行时间会浮动，不能用）

同时我们又不希望用循环 + lw/sw 指令的形式来搬运数据，于是引入 DMA 让外部设备自己写内存。这个概念凭空看是无法理解的，在现在这个语境下，实现方式就十分显然，我们修改 Bus 的设计，为其添加第二个“请求发起者”。以前总线上发起请求的线只连到 CPU。

DMA 是一个控制器硬件，和温度计没有本质区别，同样用 MMIO 被 CPU 控制（配置 DMA 的行为状态机），DMA 同样可以像温度计一样被挂起，并通过中断回复 CPU。

为避免 CPU 和 DMA 争用总线造成问题，实际会使用仲裁器作为一个硬件层调度器，决定谁有资格在同时访问一个 RAM 时先来。

CPU、DMA 与 RAM 的协作时间线

| 步骤 | CPU | DMA 控制器 |
| --- | --- | --- |
| 1 | 分配接收缓冲区 | 空闲 |
| 2 | 配置 SRC、DST、LEN | 等待启动 |
| 3 | 执行其他任务 | 持续传输数据到 RAM |
| 4 | 正常执行中 | 完成传输，发出 IRQ |
| 5 | 执行中断处理程序 | 等待确认 |
| 6 | 处理 RAM 中的新数据 | 准备下一次传输 |

现在我们消除了几项严重性能阻塞。

## 世界观 5：主板、PCIe 与设备发现

但所有硬件都是我们自己设计、自己连接的。现在假设要把这套设备变成一款产品，并允许用户购买其他厂商的网卡、SSD、USB 控制器自行扩展。

我们立即面临三个问题：
1. 不同厂商的设备应该采用什么物理连接方式？
2. 计算机如何知道新安装了什么设备？
3. 如果同时插入两张网卡，如何给它们分配不同的 MMIO 地址？

假设我们把自己设计的 CPU、内部总线、中断控制器、定时器以及几个简单设备控制器，集成在同一块硅芯片上。
这就形成了一个简化的 SoC（System on Chip，片上系统）

随后，我们制造一块廉价电路板，把 SoC、RAM 芯片、电源管理电路等安装上去。称为主板（Motherboard）。

现在，我们希望在主板上预留扩展插槽，让其他厂商可以制造网卡。我们需要约定电气和物理规格，总线通信协议等。这些标准和约定，以及为了维护这些约定而被制造于主板或者 SoC 上的硬件，共同构成了 PCI（周边元件互联）。后续的升级版点对点高速串行连接设计则称为 PCIe（高速周边元件互联）。

在 PCIe 上，我们先前设计的总线通信协议被 PCIe 硬件打包成了数据包，就像计网里做的那样，把访存操作转换成标准化的事务，在链路上传输。现在任何人都可制造能插入我们的硬件。

但是显然，我们不能要求每家网卡厂商都使用我们事先指定的 MMIO 地址。否则，两张设备很可能发生地址冲突。

因此我们在 PCI/PCIe 标准中要求每个设备必须提供一些寄存器，存放其多种相关信息用来分配编号。
我们把 PCIe 拓扑抽象成多个总线，每条总线下面有设备，每个设备又可能具有多个功能。
于是采用三个编号：
- Bus：总线编号，通常为 0～255。
- Device：设备编号，通常为 0～31。
- Function：功能编号，通常为 0～7。
三个数字组合起来叫做 BDF（Bus / Device / Function）。
通过 BDF 编号只能确定硬件的物理拓扑，不能知道其细节，因此无法启动设备，需要先读寄存器才能完成初始化配置。

我们设计的 PCIe 平台上，因此建立一个机制叫 ECAM（Enhanced Configuration Access Mechanism）。
它把 PCIe 配置空间映射到 CPU 的物理地址空间中。它是一段特殊的物理地址窗口，主机桥（这里的桥可以理解为负责连接的外围设备组件，我们无力关心其细节）会把针对这段窗口的访问转换成 PCIe 配置访问事务。操作系统由此有能力扫描 PCIe 总线，逐级发现设备。

同时，为了避免 MMIO 冲突，设备只能通过标准寄存器提供“自己需要多大 MMIO 空间”和一个 BAR（基本地址寄存器），主机完成设备发现后动态确定将哪一段地址空间映射到该设备的操作。随后对此地址进行 IO 的指令会被硬件拦截，转发到对应设备。

主机需要将分配完成后的地址写回 BAR，这样外围设备才能通过比较存储器操作指令地址，来判断消息是否发给自己。

这里说是拦截其实并不合适，因为 RAM 本身也是由此类机制做转发来被访存指令操作的，只是长期处于用户态和高级程序中，与超级大的 RAM 占用地址空间交互的经历，让我们产生了好像地址天然对应 RAM 空间的错觉。

ECAM 用来配置设备，BAR 对应设备运行时使用的 I/O 资源。 不要把这两种访问混为一谈。
由于不同的计算机平台可能把 PCIe 配置窗口放在不同的地方，实际上还需要主板平台向操作系统提供的一套标准化硬件说明与控制接口ACPI（Advanced Configuration and Power Interface）来辅助，但我们无力关心。

由于以上原因，使用 QEMU 虚拟硬件是，启动 QEMU 需要指定除了内存等经典计算机参数外的大量信息。


## 世界观 6：大容量存储

现在我们面临一个问题：存储空间不足。这个问题我们很久都没有进展，过了很久，阿波罗登月都过了几十年，~~我们依旧住不起上海的大豪斯，三代xx人住进了更大的豪斯~~存储技术取得了进步，我们获得了一种新的外围设备，磁盘或者 SSD（这里默认为 SSD）

我们已经发明了 Flash 非易失性存储器。如果把大量 NAND Flash 芯片安装在电路板上，再连接到一个专门控制它们的芯片，就可以制造 SSD。新的制造工艺终于可以制造足够大的 SSD。

回忆一下我们之前的 Flash，它已经不太简单，需要控制器，而这个新的存储设备更加复杂。查阅说明书，首先它向我们说：

为了高效存储，它据说创造了页、擦除块等概念，还会考虑磨损并屏蔽损坏。我们根本不想关心这些，这些表述在我们眼中等价于一句话：“这个存储器不能被 CPU 直接读取”。

所以我们直接翻到了使用指南这里。SSD 控制器芯片管理所有这些内部细节，接受外部命令，但这次连外部命令的这里也变复杂了。
它使用了 NVMe 这个规范，它是面向非易失性存储的主机控制接口和命令规范，可以通过 PCIe 等传输方式工作。

| 概念 | 解决的问题 |
| --- | --- |
| NAND Flash | 数据实际怎样保存（上面说过了） |
| SSD Controller | 怎样管理和访问这些存储单元 |
| NVMe | 主机与存储控制器怎样交换命令 |
| PCIe | 主机与控制器之间怎样传输事务（上文说的） |
| M.2 | 设备以什么物理形态连接到主板（接口的尺寸） |

NVMe 规范为了适应大容量存储器的物理性质，做了以下抽象：
    - 整个存储器是一组按编号排列、大小固定的逻辑块。
        - 称为块设备（Block Device）
        - 地址叫做 LBA，即 Logical Block Address（逻辑块地址）
        - 每个块这里就假设 512 B
    - NVMe 控制器可以提供一个或多个 Namespace
        - 每个命名空间都有一个 NSID（Namespace id）
        - 空间内部的 LBA 编号是独立从 0 开始的

翻到控制器部分，由于数据吞吐量大，指令不能再简单用寄存器和状态线传递。
SSD 约定启动时主机在内存（RAM）空间中建立两个环形队列：
    - 提交队列（SQ，存放待消费的存储指令）
    - 完成队列（CQ，存放已完成的指令结果）
还有一个特殊的初始队列用来执行一开始的查询 SSD 信息，建立上面两个队列等一系列指令（因为一开始还没有 SQ，CQ），这个队列本身则是像一开始那样通过 MMIO 寄存器和简单状态线建立的。

有了以上信息，我们已经可以通过 CPU 指令来操作大容量存储器，即“接入”了 CPU。和上文所说的一样，我们要为这些操作进行封装，向上提供无需关心寄存器细节的函数，也就是编写 NVMe 驱动。

我们在软件侧还会进一步抽象，定义统一的块设备接口，这样以类似物理形式存在的 SATA SSD，HDD 等也可以接入统一封装。这是后期 OS 会包含的一个组件。

现在开始设计文件系统。客户不希望一直处理这么低级的块设备，而是希望处理文件夹，路径和文件名称。
因为每个 512 字节逻辑块太小，如果文件系统要逐个管理所有逻辑块，管理数据可能会很庞大。
我们于是将连续的多个扇区组合为一个分配单位**簇**（Cluster）。

文件系统目前完全不需要新硬件，也不需要修改 NVMe 协议。它本质上是一套规定：如何利用块设备已有的读写能力，按照约定的数据格式保存文件内容和文件的管理信息。

最简单的办法，就是在磁盘上额外保存一张文件登记表，记录文件的起始簇和大小。
然而由于文件可能变更，大小可能变更，这样保存连续范围的实践不可行，修改设计：
文件登记表不再保存一段连续范围，而是保存文件的第一个簇；再额外记录每个簇的下一个簇在哪里。

改名为文件分配表（FAT），用起来类似：
```
FAT[20] = 37
FAT[37] = END
```

好了，目前为止文件勉强能存了，现在考虑目录和路径。如果用这样的登记表，进行 ls，move 目录等行为不易实现。
为了高效，我们希望有统一抽象。因此，我们的抽象模型认为目录是一种文件。具体而言就是：
- 我们为所有文件，除了记录起始簇和名称之外，附带一个类型信息，说是普通文件还是目录
- 如果类型是目录，那么实际保存在磁盘上的是一组文件登记表，保存一部分其他文件的，FAT 表中的同款信息
    - 注意到这里我们没有抛弃 FAT 表
- 如果要访问一个路径，这个路径实际上是一串目录，或者说一串特殊文件
    - 我们住个读取这些文件，在其中查找下一个文件的描述项，然后定位，再递归

为了在开机启动的时候知道应该去 SSD 上的哪里寻找 FAT 表和根目录，我们首先要能开机，然后要能找到。
将一块 SSD 分成 3 个部分，部分 0 保存分区信息，部分 1 保存启动程序，部分 2 给用户用来存放其他数据，称为分区。分区和 Namespace 并无必然关联。

分区描述信息使用一种叫做 GPT（GUID 分区表）的数据结构描述，存放在 SSD 上上述的分区 0。读取了这个信息我们就可以知道启动分区从 LBA xxxx 开始。CPU 借助固件代码读完了以后加载了启动程序，现在我们要建立 FAT 32 文件系统的存在。

FAT 32 在我们的设计下保存了一组文件系统参数，描述了分区起始 LBA，每个扇区大小等，这些都是可以配置的，所以需要保存。保存的位置总是分区的第一个扇区，这个数据叫 BPB（BIOS Paramater Block）

现在读完这个配置信息就可以知道 FAT 表和数据起始位置了。自然可以开始读取启动程序。这个启动程序是计算机的操作系统所属资源，我们还没有开始开发。但先别急，先梳理一下状况。

这套设计落地一下，我们将其称为 FAT 文件系统。

支撑我们走到现在的逻辑是独立于操作系统之外的固件代码，它同时也可以被叫做程序，或者说 FAT 32 文件系统驱动程序。它不仅可以被其他固件代码用来加载启动程序，还可以在以后启动完了之后继续被用来访问文件，屏蔽逻辑块细节。

我们准备把这台计算机卖给客户，希望客户每天按一下电源键，就可以启动某些程序。一开始我们保存在 ROM 中，后来因为不同的客户可能需要运行不同的程序（例如安装不同的操作系统，不同的批处理计算程序），我们不得不将这个启动的程序放在 SSD 中，然后费力去加载它。我们自己写在 ROM 里的则只有一些抽象功能，保存在非易失性存储介质中的软件称为 Firmware（固件）。

如果你急着追问，这里我们实现的文件系统驱动虽然是可以用的，但以后操作系统可以不用，而是用自己内部的。

总之，现在我们公司已经不太是个纯硬件公司了，我们写了很多软件，尽管它们都是固件。
我们这个时候注意到由于我们提供了充分的基础设施，有些其他公司，大学，或者是在某个神秘车库里整天不出门的 L 姓男子都在写操作系统，试图提供通用计算机功能。
隔壁公司也制造了计算机，而且它使用另一套启动固件。为了避免固件不兼容导致 OS 开发者难以工作，我们和其他公司开了个会，希望制定统一标准，即 UEFI（Unified Extensible Firmware Interface，统一可扩展固件接口）。这规定的主要是固件对于那个从 SSD 被启动的程序暴露的，由我们进行封装的硬件功能（例如分配内存，加载文件）。

这里我们跳出这个世界观，回忆一下，我们要编写一个操作系统来学习，叫 Airi-OS，为了避免过早被物理硬件的细节困住，我们使用了 QEMU
，它用 C 语言程序产物虚拟了硬件状态机行为，但如我们已经学到的，除了硬件还有固件。为了解决 QEMU 没有固件的问题，才引入另一个项目叫 OVMF（Open Virtual Machine Firmware）。

```
OVMF_CODE.fd
    │
    └── 模拟主板固件 Flash 的内容
         CPU Reset 后执行这里的固件代码

disk.img
    │
    └── 模拟一块 SSD 的内容
         固件运行后，通过虚拟存储控制器读取

真实 PC                     QEMU 虚拟 PC

真实 CPU                     虚拟 CPU
   │                            │
   ▼                            ▼
主板上的 UEFI 固件          OVMF UEFI 固件
   │                            │
   ▼                            ▼
真实 SSD                    虚拟 SSD（disk.img）
   │                            │
   └──────────┬─────────────────┘
              ▼
   固件找到 BOOTX64.EFI
              │
              ▼
   将 EFI 程序加载到 RAM
              │
              ▼
   CPU 开始执行这个程序
```

## 世界观 7：特权级与虚拟内存

现在我们继续经营这家计算机公司。新的目标是：让用户在我们的计算机上同时运行多个程序，而且一个程序发生错误时，不应该破坏其他程序或整个计算机。之所以需要这样是因为那些 OS 开发者通过我们的接口启动了大量的复杂程序，并且遇到了软件设计无法解决的问题。如果我们不修好，就会被抢走市场份额 ~~，然后倒闭，创始人散伙，工资花完以后穷困潦倒，最后只能去卖钩子~~

如果程序 A 是温度计记录程序，而一个未经授权的程序 B 应该不能访问温度计数据，我们无法做到，我们当然可以规定“程序 B 不允许操作温度传感器”，甚至在程序 B 的源码里增加检查。
但这没有意义：用户完全可以修改程序 B，绕过这些软件检查，直接执行机器指令，这是因为目前所有的控制权都被交给了指令。

现代法理学和宪政主义有以下表述：

> “不存在可以约束自己的绝对权力；若其能被约束，则其权力不绝对；若其权力绝对，则其限制无效。”

解决方案是权力分立，在这里意味着我们需要作为硬件厂商夺走一部分软件权力。

首先我们设计一个寄存器，表示机器特权级：

| RISC-V 模式 | 用途 | x86 近似对应 | 说明 |
| --- | --- | --- | --- |
| M-mode（Machine） | 机器级控制，通常用于底层固件 | 无直接对应；固件可在实模式/高特权环境运行 | x86 没有与 M-mode 完全等价的模式 |
| S-mode（Supervisor） | 操作系统内核 | Ring 0 | 操作系统内核 |
| U-mode（User） | 普通用户程序 | Ring 3 | 普通用户程序 |

假设程序 B 合法的需要读温度计，那么要求它通过我们刚增加的一个特殊指令 ecall 来请求跳转到内核处理入口。如何跳转和保存状态由硬件和软件层分别负责保存各自关心的，这个跳转用的就是我们先前建立的中断机制。

目前程序 B 不能随意修改特权控制状态（因为这个状态由指令不可达到硬件托管）

但是地址尚未被保护，普通指令可以完成任何地址读写，若程序 B 异常，可能经 MMIO 等机制产生越权操作。
同时随着高级语言出现，抽象程度更高，一个编译器可能编译出字面上访问相同地址的程序，把分配实际地址的职责交给我们。
并且，RAM 开始不够用，我们可能需要虚拟出比 RAM 更大的空间，使得计算机可以使用大于 RAM 大小的空间。

出于以上需求，我们引入虚拟地址，彻底改变软件层地址的含义，通过我们制造的 MMU（内存管理单元）来完成这个映射。
运行哪个程序、分配哪块 RAM，是操作系统在运行过程中才能决定。
我们再次采用熟悉的办法：将规则写成普通数据，保存到 RAM，让硬件按照这份数据工作。
这份数据叫 Page Table（页表）。

假设要为每一个字节记录地址转换关系，映射信息会非常庞大。
我们于是约定：每连续 4096 字节作为一个整体进行映射。
簇是文件系统分配磁盘空间的单位，页是内存地址映射与保护的单位。两者属于不同系统，并非重复劳动。

现在我们在页表项里增加几个标志：
R = 是否允许读
W = 是否允许写
X = 是否允许执行机器指令
U = 普通用户模式是否允许访问

页表只能由操作系统进程在 S-mode 或者说 Ring-0 下操作。
现在即使程序 B 知道温度计的 MMIO 地址，也无法通过页表查找检查。
MMU 发现地址无法合法访问时，会使 CPU 触发 Page Fault（页故障），操作系统内核负责决定如何收场。

在计算机组成原理课上讲过页表分级，以及 TLB 页表缓存，这些属于硬件技巧和优化，我们交给实习生做完就可以了。


## 世界观 8：发明链接器与 ELF

现在我们已经解决了大部分硬件层问题，现在主要问题在于软件过于难以开发。

首先我们是像原来一样，把汇编语言裸文本直接保存为文件，并指定 CPU 从头部开始执行。
然后是第一个问题，我们需要让软件由多个程序文件组成，以便解耦合并便于多人协作。
为此首先引入程序文本的分段。这里的程序文本是低级可执行文件，而不是高级语言源代码。

`.section` 字符串：汇编器保留字，用于声明后续一段内容放在哪个段
`.text` 段：保存需要执行的机器指令。
`.data` 段：保存有初始内容、运行时可以修改的数据。
`.bss` 段：为运行时需要的零初始化数据保留空间。避免利用 data 段存储大量空数据。

现在我们要将一个函数放在 A 文件，另一个函数在 B 文件里调用，面临的问题是跨文件无法确定函数代码所在的内存地址。
这个地址只能由 OS 动态分配，因此引入一种中间产物文件，让 OS（准确来说是链接器，OS 的一个组件）来在程序载入内存之前填写地址。填写之前，这些地址上的占位符就是符号（Symbol）。
这个中间产物文件就叫做目标文件，后缀`.o`，不可执行。

链接器是一个硬件无关的软件，为了使其在我们的硬件平台上工作，我们需要提供一个配置文件，说明地址布局要求，即`.ld`后缀的链接器脚本文件。
我们的链接器脚本需要指定的要求包括：
1. 程序的执行起点是哪个标签（一般是`_start`）
2. 指定起始地址，数据对齐等
3. 将代码和数据分别组织为两个可以被加载的区域

这个时候链接器已经生成了代码中待填写的数据，但加载程序还需要知道将哪些内容放到哪里。
于是我们不再把可执行文件简单视为一段连续机器码，而是把它视为“程序的数据内容 + 如何将这些内容变成运行中程序的描述信息”。
具体而言，这些描述信息包含程序入口地址，代码在文件中的位置，代码在 RAM 中的位置，代码长度，数据在文件中的位置，数据在 RAM 中的位置，数据长度，还需要额外清零多少内存等。这些数据全部由链接器填写。

这些规范设计完成后，我们将其命名为 ELF（Executable and Linkable Format）。

我们最开始把不同的源码分别汇编成 .o，需要区分代码、常量、全局数据和未初始化数据，以便链接器合并、安排地址并进行符号解析。
所以我们设计了 Section（节）。
但程序最终加载时，加载器并不需要关心每个函数属于哪个源文件，也不需要知道所有符号名称。它只需要知道哪些文件字节应该复制到哪些内存位置。
所以我们又设计了 Segment（段）。这是 ELF 中的数据布局情况，一般我们甚至读不到。

现在加载器的任务是：
- 读指定文件的 ELF 头
- 根据 ELF 头找到程序头表，并遍历其中的每个表项（Program Header）：
    - 如果表项的类型不是 `PT_LOAD`，就跳过
    - 将文件中从 `p_offset` 开始、长度为 `p_filesz` 的内容复制到内存地址 `p_vaddr`
    - 如果 `p_memsz` 大于 `p_filesz`，将 `p_vaddr + p_filesz` 开始、长度为 `p_memsz - p_filesz` 的内存清零
- 所有可加载段处理完成后，跳转到 ELF 头指定的入口地址 `e_entry`

实际操作更加复杂，加载器需要安排物理内存，建立页表映射，检查合法性，对齐等细节。


`.ld` 脚本的编写者通常是该项目/平台的开发者、OS 内核作者、BSP/SDK 提供者，或者裸机程序员自己。


这里我们再次临时跳出世界观，我们编写 Airi-OS 的启动过程可以这样划分：
```
CPU 通电
    │
    ▼
主板 UEFI 固件
    │
    │ 找到启动文件
    ▼
BOOTX64.EFI
    │
    │ UEFI 加载并执行它
    ▼
Limine 开始运行（这也就是加载器程序，BootLoader）
    │
    │ 读取 kernel.elf
    │  解析 ELF
    │  把代码和数据装入内存
    │  建立需要的分页映射
    ▼
跳转到内核入口
    │
    ▼
Airi-OS Kernel
```
这里 UEFI 固件和 Limine 实际上都涉及“加载程序”，但它们负责的文件格式和启动约定并不相同。
UEFI 通常通过固件中的映像加载器装载 BOOTX64.EFI。x86-64 UEFI 应用采用 PE/COFF 体系中的 PE32+ 格式，它与 ELF 本质一样，但采用不同的数据结构。

随后，在我们的 Airi-OS 启动方案中，Limine 负责加载内核。我们将 kernel.elf 编译为 ELF 可执行映像，Limine 就可以依据 ELF 的装载信息安排内存。

现在返回原本的世界观。


## 世界观 9：BootLoader

公司已经生产了 16384 台计算机，所有机器都使用我们设计的 UEFI 固件。
现在有两家软件开发实体：
- 我们编写了 Airi-OS，内核采用 ELF 格式，需要在高半区虚拟地址运行。
- B 公司编写了另一个操作系统，使用不同的可执行格式、内存布局和启动约定。
我们当然可以不断修改固件，让它同时理解所有操作系统。但固件更新很困难，我们希望固件只提供稳定、通用的启动环境，而把特定操作系统的装载工作交给另一个程序。

于是设计：
```
CPU 通电
    │
    ▼
启动固件
    │
    │ 负责硬件初始化
    │ 找到并启动一个标准格式的程序
    ▼
第二个程序
    │
    │ 了解操作系统内核的格式
    │ 安排内存和执行环境
    ▼
操作系统 Kernel
```

我们编写的这个负责把操作系统内核准备好并启动的程序，就叫 Bootloader（引导程序）。
这个程序有很多种实现，这里我们就起名叫 Limine。
Bootloader 没有特殊的硬件身份，也不是 CPU 必须支持的一种执行模式。
它仍然是一段普通机器码，只不过承担了加载内核和交接控制权的任务。
它也不是所有计算机都必须拥有的独立组件。某些简单设备的固件可以直接启动内核。

UEFI 对 EFI 可执行程序制定了统一格式和启动接口。在我们开发的 x86-64 平台上，这种文件通常采用 PE32+ 可执行格式。
不用关心它具体是什么，就理解为 ELF 的另一种平替即可。

我们在制定 UEFI 规范时，要求固件提供一套通用的程序装载服务，其中包含：
```
LoadImage(...);
StartImage(...);
```

实际发生的过程是：
```
UEFI 固件正在运行
    │
    │ 通过文件系统读取 BOOTX64.EFI
    ▼
UEFI 的 PE 映像加载器
    │
    │ 分配 RAM、加载代码和数据
    ▼
StartImage()
    │
    ▼
CPU 进入 BOOTX64.EFI 的入口
```

对于我们的 Airi-OS 启动介质，BOOTX64.EFI 正是 Limine 的 UEFI 版本。
这时 CPU 开始执行 Limine 的机器码。
但固件并没有从内存里消失，也没有创建一个类似 Linux 进程的新进程。 CPU 只是从固件代码进入了另一个已经装载好的程序。


UEFI 在启动 EFI 程序时，会传入一个 EFI_SYSTEM_TABLE 指针。
它包含一套可供 EFI 程序调用的固件接口，例如：分配内存，获取内存布局等。
这些函数由固件实现，并非 Limine 自己实现了所有底层硬件操作。


现在 CPU 已经进入 Limine，但它仍然不知道要启动什么程序。
于是我们给 Bootloader 增加一个配置文件，描述用户希望启动的操作系统。
这个配置文件存储于 SSD 上，记录有哪些可用的操作系统，其内核的 ELF 文件分别在什么位置。

Limine 还需要完成的工作包括：
- 配置 CPU 用于记录内存页表位置的寄存器
- 在 RAM 中分配栈空间并配置 RSP 寄存器
- 配置特权级寄存器

Bootloader 的工作不止于简单的“把文件复制进 RAM”，还包括按照约定将内核装入内存，再把 CPU 调整到内核能够立即执行的状态。
（也可以说是建立 C 语言运行环境）

Limine 已经成功加载内核。
接下来内核要实现自己的物理内存分配器。
可是，内核刚刚启动，它不知道整台机器有多少 RAM，也不知道哪些 RAM 被固件、内核自身和其他平台组件占用了。
因此我们要求 Bootloader 向 Kernel 提供一份 Memory Map（物理内存布局信息）。
Bootloader 进入 Kernel 时，会按照约定把一个指向 BootInfo 的指针放在指定 CPU 寄存器中。
这就称为引导协议。实际上可以采用不同的约定，因此需要指定内核采用的引导协议。

这里我们的 Linime 让 Kernel 预先声明自己需要什么信息，再由 Limine 在启动前准备对应的数据。Kernel 只是读取 RAM 中已经被填写好的数据结构。

内核开始运行以后，也想自己管理 RAM。
如果固件和内核都认为同一块内存可以自由分配，就可能互相破坏数据。
因此，我们必须设计一次明确的交接：
从某个时间点开始，固件不再提供启动阶段的内存和设备服务，后续系统资源交由操作系统管理。

UEFI 已经标准化了这个操作，叫：
```
ExitBootServices(ImageHandle, MapKey);
```

此外，内核进入时不能假设已经存在一套可以直接使用的 IDT（中断描述符表，即我们第四阶段为了处理硬件中断所需要的入口配置）。这部分需要内核自行建立。

完成以后，Limine 最终把 CPU 控制流转移到内核入口。


## 世界观 10：内核接管

现在，CPU 开始执行 Airi-OS 编译出的 ELF 文件所指定的入口函数。
为了让我们自己开发的操作系统可以运行，我们的任务是让内核逐步摆脱对 Limine 所提供环境的依赖，最终能够自己管理内存、处理异常和控制设备。

CPU 大致处于以下状态：
```
CPU
├── RIP → kmain（内核 ELF 入口函数） 的机器指令
├── RSP → Limine 准备的栈
├── CR3 → Limine 建立的页表
├── 执行模式：x86-64 Long Mode
├── 特权级：Ring 0
└── 可屏蔽外部中断：关闭

RAM
├── Airi-OS 的代码与数据
├── Limine 准备的启动信息
├── 当前正在使用的栈
├── 当前正在使用的页表
└── 其他尚未分配的内存
```

现在能执行 C 函数，并不代表我们已经拥有 C 程序平时依赖的完整运行环境。
我们的 C 运行环境是不完整的，现在可以分配栈上变量，可以进行全局变量访问，可以计算，但无法分配堆内存。
`malloc()` 并不是 CPU 指令，也不是 Limine Boot Protocol 提供的内核服务。它是一种软件内存分配接口，需要有实际的分配器实现支撑。

Linime 留下的交接信息说明了内存区域可能是以下状态：
- USABLE：目前可供内核使用的物理 RAM。
- EXECUTABLE_AND_MODULES：包含已经加载的内核及相关模块，不能直接重新分配。
- BOOTLOADER_RECLAIMABLE：包含引导阶段使用的数据，可以在确认不再依赖后回收。
- RESERVED：保留给平台或其他用途，不能随意访问。

这些都是物理地址，不是虚拟地址。
看第三个 BOOTLOADER_RECLAIMABLE ，它不能立即使用，Limine 准备的栈空间，页表和启动信息都在里面。
这些东西仍然正在被我们的内核使用。

如果现在把它们所在的 RAM 重新分配给其他用途，后续函数调用、页表翻译或者读取 Memory Map 都可能出错。
因此我们采用更安全的策略：
第一版内存分配器只使用 USABLE 区域。所有 BOOTLOADER_RECLAIMABLE 区域暂时保留。
等到我们有了自己的栈、页表，并处理好仍需保存的启动信息，再考虑回收它们。
这一步很重要区分了两个概念：
- Limine 已经不再执行。
- Limine 留下的内存数据已经不再被使用。
第一件事情已经发生并不代表第二件事情也成立。


我们现在向那些在无现代操作系统的，从我们这里买的计算机上，开发程序的用户做市场调研：
客户提出一个需求，以后内核想获得新的内存时，希望能调用 `uint64_t physical = alloc_page();`

这时我们面对的问题已经简单很多，大部分基础设施都造好了。我们可以用高级的 C 语言写一个内存分配器，它有一个 next 全局变量，用来指向空闲区域，每次被要求分配函数，就改变这个变量并返回。这个变量当然会被直接编译进 ELF 文件，由 Linime 加载。

具体怎么写本项目以后再说。

还要考虑一个问题，我们已经发明了虚拟地址，因此返回的也是虚拟地址。我们的 CPU 已经启用了 MMU。C 指针保存的是 CPU 访存使用的虚拟地址。它不会自动把 0x00400000 解释成物理地址。如果页表项不存在，Page Fault 我们目前也无法处理（因为还没有写这个 OS 组件），因此机器会停机。

我们首先让内存分配器直接去改写页表。这让第一次内存分配成功。

但我们现在要制造的是一个操作系统，后续会频繁分配物理页，例如用于内核数据结构、进程内存、页表自身等。
如果每次 `alloc_page()` 返回一页物理内存，我们都必须先单独建立一个虚拟地址映射，才能访问它，就会有些麻烦。
更重要的是，我们如果要编写一个页表管理器，它本身也需要分配 RAM 来保存页表。假如连这些新分配的 RAM 都无法访问，我们就要先解决页表管理器的自举问题。

于是在内核开始运行之前，我们就希望提前把所有准备交给内核管理的物理 RAM 映射到一片约定的虚拟地址区域。

我们修改了 Limine 的 Boot Protocol，要求其建立一段初始页表，将允许访问的物理内存，按照固定的地址偏移，映射到虚拟地址空间的一片连续编号区域中。
我们把这片映射放在 x86-64 的高半区虚拟地址空间。
```
0x0000000000000000
        │
        │ 低半区
        │
0x00007FFFFFFFFFFF

    中间的地址不符合该模式的一小段区域

0xFFFF800000000000
        │
        │ 高半区
        │
0xFFFFFFFFFFFFFFFF
```
这台规则被称为 HHDM（高半区地址映射）。

这里的高半区并不意味着 RAM 在物理上处于什么高地址位置。
它只是我们选择使用虚拟地址空间的高地址区域。我们可以把物理地址 0x00400000 对应的 RAM，映射到虚拟地址 0xFFFF800000400000。
**Higher Half Direct Map（HHDM，高半区直接映射）**：
- Higher Half：映射放在虚拟地址空间的高半区。
- Direct Map：虚拟地址与物理地址之间采用固定偏移关系。

同一段物理地址可以以两种方式被寻址，占用两份虚拟地址空间，直到我们清理 Linime 残留（也可以不清理）。第一条是内核代码自身的映射，第二条则是 HHDM 映射。

接下来要做的就是纯内核开发工作了，本文档完结撒花！


## 补充：关于 QEMU

首先，由于真实硬件只能使用物理水平的超低级调试手段，我们无法在真实硬件上高效学习。
这里我们不得不用 QEMU，因此我们需要重新理解阶段 0。

QEMU 的编译前，编译后，启动时，运行时形态分别是什么？

它在编译前可以视为一个 C 语言项目。真实的硬件由大量的标准化硬件零件拼接而成，例如你武计院本科数电提到过的 74LS153 等，它们显然是一些有限状态机。
QEMU 的代码就是在用 C 语言模拟这些有限状态机的行为。

QEMU 的编译后形态是平平无奇的 ELF，Mach-O 等可执行文件。
它有命令行参数，可以像其他程序一样启动，也就是说它初始化自己的进程。
然后它创建一个特别的虚拟机对象，这个对象包含了其源代码模拟的各种硬件模型数据成员。
